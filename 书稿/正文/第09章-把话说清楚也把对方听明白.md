# 第9章　把话说清楚，也把对方听明白

工作里的事，大半要靠说话来推动：对需求、问问题、聊方案、报进度，一天下来，说的话比写的代码多。话没说清，或者没听明白对方的意思，事情就会走样：问题发出去半天没人回答，评审会上各说各话，一句话把协作方惹火，接下来几天都在收拾它留下的局面。

说话这件事，上学的时候没人教，也不算成绩；到了工作里，它跟写代码、做方案一样，是天天都在用的本事。有人觉得会沟通靠天赋，有人把它等同于圆滑世故，其实都不是。把话说清楚，让对方接得住；把对方听明白，听到话背后他要的东西。这两件事都有具体的做法，都能练。

## 1. 提问前，整理背景、自己的判断和具体卡点

最日常的沟通，是遇到不会的事开口问人。同样是问，有的问题别人一看就能搭上手；有的问题发出去，对方半天不回，回了也是一句反问：你到底想干什么？

我班主任的女儿学金融，实习时带教含糊地交代了一个自动生成 Word 文档的任务，她没问清楚就答应下来，回头来问我有没有现成的代码。单看她发给我的那个问题，就够我犯难的：一句“有没有用 Python 一键生成 Word 模板的代码”，外加一个我没听过的插件名。她在做什么事，为什么要生成文档，自己试过什么，一概没有。我盯着那句话看了半天，不知道从哪里帮起。

她的问题不只是没把背景告诉我，连她自己也没问清带教到底要做什么，却直接跳到了找代码这一步。这样的问题发过来，我既不知道任务是什么，也不知道她缺哪一块知识。想帮忙，得先把前因后果一点点问出来。大家手头都有自己的事，看到这样没头没尾的问题，往往无从回答。

所以，自己不清楚的任务先回去问清楚，已经知道的背景也要告诉帮忙的人。一个别人接得住的问题，带三样东西。一是背景，一两句就够：我在做什么事，为什么做。二是自己的判断和尝试：想到了哪一步，查过什么，试过什么。三是具体的卡点：卡在哪里，希望对方给什么，一个答案，一个思路，还是一份资料。拿她的事来说，问清任务后，假如带教要的是把已有数据填进固定模板，就可以这样问：“带教希望把表格里的数据填进 Word 模板，省掉手工复制的工作。我查到 Python 有处理 Word 的库，但不知道怎样把数据填到模板指定的位置，有没有可以参考的例子？”这样一说，对方就知道该从哪里帮起。

问题还可以拆细。把事情拆成几块，说清楚哪几块自己能搞定、哪一块想不通，比一句“这个该怎么办”好接得多。对方一眼看到问题的边界，帮忙的负担小，愿意接的可能就大。

粒度也要选对。上来就请人帮忙写一段完整的程序，这不是提问，是把任务甩给对方，谁看了都想绕着走；换成“我刚开始学这块，有什么推荐的入门材料”，几乎人人都答得上。问题越笼统，能接住的人越少；越具体，帮起来越省力，对方也越愿意帮。

问之前把功课做完，做完之后怎么开口，就是这三样：背景、自己的判断、具体的卡点。花几分钟把它们整理成几句话，换来的是问题真的有人接。

## 2. 听懂要求背后的诉求，减少各说各话

提问是自己开口，反过来，别人向自己提要求、发质问的时候，考验的就是听：能不能听出对方真正要的是什么。

一个周一的早上，团队里一位入职不久的同事，在群里直接跟产品经理说：某个功能不好支持，请产品评估一下是否可以下掉。产品经理当场就炸了，质问为什么这个功能在别的场景都正常，唯独这个场景不行。我赶紧出来解释：这个功能有好几处地方调用，每处传进来的数据有些差异，出问题的这一处正好少传了一个关键数据，所以用不了；我们拉后端一起看看，争取把几处传的数据统一起来。产品经理这才缓和下来。

同事说错了吗？单看技术判断，没有错，那个场景确实不好支持，他说的是实话。可产品经理听到的不是技术判断。功能是他提的需求，能不能正常上线、正常运行，是他工作里最基本的一件事；“不好支持，建议下掉”这句话，在他听来就是“你的功能要没了”，而且不带任何原因，也不给出路。踩了人家最要紧的事，又没留退路，对方只能跳起来。

这就是各说各话：一边说的是技术能不能支持，一边听到的是自己的功能保不保得住，两边想的根本不是同一件事。

要减少这种局面，就得看到要求和质问背后的诉求。拿产品经理来说，最基本的诉求是提的需求能按时上线、正常运行；再往上，是功能少出问题，不用整天被 bug 缠着；再往上，是需求被认可、给业务带来增长，自己也跟着成长。平时打交道的每一句话，多少跟这些有关。他质问“为什么别的场景正常”，字面上是个技术问题，背后要的其实是“我的功能还能不能用、什么时候能用”。如果回应时只看到字面问题，就会去争论技术细节；而如果看到背后的诉求，就先讲清楚原因，再给一条路径。我那天的解释能让他缓和下来，靠的就是这两样。

诉求不用一个一个去分析。跟自己天天打交道的，像产品经理、上下游的开发、测试，值得花心思弄清楚他们最在意什么；一年碰不上几次的，用到时想一想就行。

说出口之前，也可以倒过来想一层：这句话在对方听来是什么意思？会不会正好踩在他最在意的事情上？多想这一层，很多冲突根本就不会发生。

## 3. 表达不同意见：拿出依据、取舍和备选方案

沟通里最考验人的时刻，是意见不合。有时是对做法有不同看法，觉得这个方案不对；有时是对分工不满，觉得这件事不该我做。不管哪一种，都绕不开同一个问题：话怎么说，既表达了立场，又不把关系谈崩。

我遇到过一次分工上的分歧。有个需求上线后，数据的格式变了，老数据要想继续用，中间得加一段兼容的处理。这段逻辑放在前端做，或者放在后端做，技术上都行得通，两边也都不想接：加的工作量不大，但维护是长期的。这种谁做都行的事，最容易谈出火气。

去找后端谈之前，我先想清楚了几样东西：最好的结果是后端来做，因为数据在后端统一处理，几个调用的地方都能受益；实在谈不下来，我们前端自己做也能接受，但方案要尽量简单，这是底线；放后端为什么更合理，理由要摆得出来；万一后端确实排不出人手，前端接手可以怎么简化，这是备选。这些不用写成文档，脑子里过一遍，几分钟的事。

谈的过程反而简单。我把放后端的理由讲了，对方也有难处：他们手头的排期已经满了，腾不出人。来回几轮，最后定下来这次由前端做，不过讨论里找到了一个比我原先设想简单得多的实现，我担心的维护问题去掉了大半。这种时候还可以把话说在前头：这次的兼容我们做了，下次再有类似的情况，可就轮到你们了。半开玩笑的一句话，真到下次，就是现成的说法。

看结果，这次是我让了步；但整个过程没有伤和气，我的顾虑也解决了大半。能做到这样，靠的是事先想清楚的那几样东西：心里有底线，对方没越过底线，就可以一直保持商量的态度，不用急，也不用把话说死；手里有依据，摆得出每个方案的代价，放前端维护难在哪，放后端要占谁的人手，再备着退一步的选项，谈的就是事情本身，而不是嗓门和态度。

对方案的不同意见，做法是一样的。觉得同事的技术选型不合适，别只说“我觉得不行”，把依据摆出来，比如这个库多久没人维护了、我们的场景里它有什么问题，再给一个备选。有依据、有备选的反对，对方接得住，也愿意认真对待。

这套准备不看资历，刚工作的人也做得了。当然，谈的结果不只取决于准备，也取决于双方的位置和当时的环境，准备充分也可能谈不成；但有准备和没准备，对方对待这场谈话的认真程度会完全不同。还有一条要记着：不是每件小事都值得争。争有争的成本，时间、精力、关系都是；掂量下来不值得的，让一步也没什么。值得争的，就把依据、取舍和备选备齐了再开口。

## 4. 用开放的表达与合适的沟通方式，减少误解和对抗

提问、听懂对方、表达不同意见，说的都是在不同场景下讲什么；同一句话用什么方式讲出来，是另一件事。方式不对，内容再对，对方接收到的也只有对抗。

团队里的小 Q 有一次跟我反馈，说我老是反驳他的建议，让他觉得有点受打击。我的第一反应是不服：他刚入职不久，提议常常跟团队的实际情况对不上，否掉是有道理的。可再一想，这事没那么简单。技术方案上我有决策权，我们俩的位置天然不对等；我以为自己只是就事论事，可从他那边看，每次开口都被上面的人一句话顶回去，时间长了，谁还愿意开口？

之后再跟他讨论，我改了方式。他的提议有道理时，我不急着下结论，先请他展开：“如果这个模块让你设计，你会怎么做？”听完先说哪里可取，再补上他没考虑到的现实情况，最后照他的思路去做，让他在这个基础上再优化。他的提议不靠谱时，我也忍住不当场否定，搬把椅子坐到他旁边，花半个多小时讲清楚现在的设计为什么是这样：当初遇到过什么阻碍，做过哪些权衡。他听完接受了现在的方案。我多花了半个多小时，换来的是他之后愿意说的话明显多了。

我把这种做法叫作示弱：位置强的一方有意把姿态放平，用商量的方式说话。名字里带个“弱”字，学的却不是低头：我的判断没有变，该指出的问题照样指出，变的只是说法，把“不行”换成“你会怎么做”，把结论换成理由。

放平姿态不只是带人的人要练。跟同事讨论方案，说“你这不对”，和说“这里我理解是这样，你看是不是漏了什么”，内容一样，得到的回应完全不同。前一种说法把人推到对立面，后一种给双方都留了空间：我可能有没考虑到的，你也可以补充。位置越强势，越要注意这一点；刚工作的人也有自己的强势时刻：带实习生的时候，面对不熟悉这块业务的协作方的时候，一样用得上。

除了怎么说，还有在哪儿说。前面砍功能那件事，那句话除了内容踩了对方的诉求，还有一个问题：它是在群里说的。当着一群人的面，功能被提议下掉，产品经理就算想心平气和，也得先顾及面子。分歧和坏消息，能当面谈就当面谈，能私下说就私下说；复杂的事情，拉个小会比在群里来回敲字强。表扬和结论可以公开，问题和分歧尽量私下。

说到底，开口是为了把事情谈成，不是为了把对方驳倒；话怎么说、在哪儿说，都是为这个目的服务的。

---

沟通的技巧讲起来很多，落到日常，就是开口之前多想一步。下一次把问题发出去之前、把反对说出口之前，先问自己一句：这句话，对方接得住吗？
