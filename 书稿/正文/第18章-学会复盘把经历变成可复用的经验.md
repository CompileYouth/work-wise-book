# 第18章　学会复盘，把经历变成可复用的经验

线上出了事故，过几天，相关的人被拉进会议，依次说明原因和改进措施，气氛像一场自我审判。很多人对复盘的全部印象就来自这样的会：出了事，开会追查一遍，写一份整改报告交上去。没出事的时候，谁也想不起这两个字。

其实复盘的本意不是这个。复盘是从围棋里借来的词。一盘棋下完，棋手把对局重新摆一遍，哪一步走得好，哪一步是败招，逐一分析。棋手不是输了才复盘，赢了也复盘；分析的也不只是错误，好的下法同样要弄明白，下次才用得上。工作里的复盘也一样，小到一个任务，大到一个项目，做完都值得回头看一遍。

## 1. 工作三年，怎样避免只是在重复第一年的经验

简历上写着“三年工作经验”的人很多，但这三年积累下多少真正的经验，每个人不一样。有人做了三年前端开发，真正在学新东西的只有前半年，后面两年半，用的都是前半年学会的那些增删改查。有一个办法可以检验：想一想，假如后面那两年半什么也没有做，现在的能力会不会有差别？差别不大，那两年半就只是重复，算不上经验。

很多经历无法变成经验，问题出在教训记得太具体。我刚工作那年吃过这样的亏：改完代码，在自己电脑上简单验证之后就上线，结果线上出了问题。我给自己记下一条教训，以后上线前，先在测试环境完整跑一遍。过了一段时间，我上线一个配置改动，心想配置又不是代码，没有走测试环境，又出了问题。前一条教训没有记错，可它只覆盖代码的改动。当时要是多问自己一句：问题的根源是什么？答案其实很清楚，都是没有经过验证的改动进了线上环境。教训要是写成“任何改动上线前都要经过验证”，配置这一次的问题就能够避免。复盘要做的就是这件事：不只记住这一次的教训，还要举一反三，想清楚它属于哪一类问题，把教训总结到能防住这一类问题的程度。

复盘还有一个作用，是给自己反馈。学东西最快的阶段，是有人持续给出反馈的阶段：方案拿给导师看，他指出问题，改完再拿给他看。可没有谁能一直得到这样的机会，工作越久，主动给你反馈的人越少，越往后，反馈越要靠自己给自己。桥水基金的创始人达里奥坚持复盘几十年，《原则》里那几百条原则，就是他把工作和生活里的经历一件一件复盘之后积累下来的。

所以复盘不必等出了事才做，也不必做得很隆重。一个任务收尾，花十几分钟回想一遍，写下几条记录；一个项目结束，跟参与的人坐下来把过程梳理一遍，就足够了。

## 2. 还原目标、过程和结果，识别关键判断与偏差

复盘的第一步是还原：把当时的目标、中间的过程、最后的结果，照实写下来。

有一次，一位运营同事小 K 通过站内信给几万名特定用户定向投放了一份问卷，几个小时过去，问卷的阅读量是零。她怀疑系统有故障，请我排查，而我在这之前完全没有接触过这套投放系统。我把投放到回收从头到尾拆成六个环节：运营圈选用户，名单上传到投放系统，投放前用内部账号试发验证，系统向名单里的用户发送，用户看到站内信提醒，点开问卷。然后逐个环节排查，经过一通仔细的排查，其他五个环节依次排除，最后范围缩小到了剩下的一个环节：上传的名单。这个环节我一开始认定最不可能出错，一直把它留在最后。请后端同事拿名单和投放数据核对，原因竟然出在这里：名单里每个用户 ID 的尾部多了一个空格，系统找不到这样的用户，一条都没有投出去。

事后复盘，我先把这件事写下来：当时的目标是找到零阅读的原因，中间六个环节怎么拆解、哪些有验证结果、哪些还查不清，最后问题出在名单的空格上。还原要如实记录，当时怎么判断的就怎么写，不用事后的眼光去修饰；记忆靠不住，要多对照当时的聊天记录和数据。

还原之后，把关键的判断逐一检视。哪些地方做对了，要写下来：把投放拆成六段再逐段排查，这套分而治之的做法，让一套完全陌生的系统也有了入手的地方；请小 K 帮忙验证、请后端核对数据，没有独自埋头排查，节省了大量时间。判断出现偏差的地方，更要写下来：我认定小 K 投放经验丰富，她提供的名单不会有问题，把名单留到最后才排查，问题恰恰出在那里。按可能性排序本身没有错，错在我想当然，没有想到名单的来源变了。出现偏差不奇怪，复盘的价值就在于把它找出来。记下这一条，下次再排查问题，我就会先问一句：这份数据是从哪里来的？

## 3. 从现象追到原因，进一步看见流程与协作中的问题

还原做完，判断也检视过了，复盘还差一步：向下追原因。还是站内信那件事，查到名单里的空格，只是找到了这次故障的直接原因，向下还有几层可以追问。为什么名单里会有空格？一问才知道，这份名单是从另一个系统导出的，那个系统导出的数据，每条尾部都带一个空格；以前没有人从那里导出过名单，所以一直没有出过问题。再问，带着空格的名单为什么能一路投放出去？因为后端只负责发送，从不检查名单里的用户是否存在，坏数据一路畅通。还可以再问，为什么几个小时之后才从阅读量发现异常？投放前明明用内部账号验证过，却没有核对实际导入的用户 ID 能不能被系统识别，投放后也没有及时确认这些用户的发送结果。就算在正式名单里另外加几个正确的内部账号，也发现不了其他 ID 尾部的空格。检查要覆盖真正出错的那一步。

只盯着现象，能做的是把这一次名单里的空格清理掉；知道了空格从哪里来，会去修正那个系统的导出格式；看见了流程里的缺口，才会想到在导入时检查实际名单，把格式不符、找不到对应用户的记录报出来；投放后再核对发送结果，及时发现失败的情况。

商业顾问刘润把这三层总结为：“普通人改变结果，优秀的人改变原因，顶级优秀的人改变模型。”

这三层里，最后一层最难看见，我自己也是吃过亏才明白。我负责过一个在很多场景里复用的模块，样式经常被改出问题，改了这个场景，那个场景就受影响。一开始我们出一个问题就修复一个，为了不影响别的场景，只好不断增加判断条件，代码越改越复杂。后来我停下来把原因梳理了一遍，发现根源不在样式本身，而在页面结构太混乱，于是重新设计了这个模块的结构，定下使用规范。规范落地之后，这一类问题基本消失。回头看，逐个修补只是在改变结果，找到页面结构这个根源才算改变了原因，而那份规范把以后的写法都确定了下来，改变的是模型。

向下追问的时候，我习惯多问一句：还可能是谁的问题？是操作的问题，还是数据、系统或者流程的问题？这样问是为了打开视角，不是为了把责任推给别人。当然，也不是每个问题都值得追到底。追到多深，看它重复的频率和造成的代价：偶然发生的小麻烦，记录一条就可以；反复出现、代价不小的，才值得回头重新审视整个流程。

## 4. 写下适用条件与下次的改法，在新实践中验证经验

原因追查出来了，最后一步是写下来，写成下次能直接使用的东西。偏偏这一步最容易出问题。古人的道理为什么单独听都对，放在一起就互相矛盾？“先下手为强”和“后发制人”，“宁为玉碎，不为瓦全”和“留得青山在，不怕没柴烧”，两两相反，却都流传了千年。不是道理错了，是它们都省略了背景条件：什么时候该抢先，什么时候该等待，各有各的场合。复盘写经验，最怕也写成这种没有条件的格言。

以空格那件事为例，经验该怎么写？写成“下次投放前检查有没有空格”，只防得住空格这一种情况，下次出问题的可能是编码，可能是换行符，一条一条防不过来。只写“所有数据都要校验一遍”，又没说明到底校验什么。合适的写法带着条件和动作：名单是跨系统流转来的，导入时按目标系统的要求检查整批 ID 的格式和有效性，把不合要求的记录找出来；首次使用一个新的名单来源，还可以抽几条核对，确认目标系统识别到的是预期用户。什么情况下适用，具体做什么，两项都写清楚，这条经验下次才用得上。

写下来还没结束，复盘得出的，严格说只是一种解释：当时那样做吃了亏，不代表换一种做法就一定行得通，解释可靠不可靠，要等下一次实践来检验。样式规范定下来的时候，我也只是判断它能解决问题，直到它使用了几个月，同类的问题确实不再出现，这条经验才算经受住了检验。要是验证不顺利，就回头修正解释，这本身又是一次复盘。所以记录经验的时候，最好注明它验证过没有，日后再使用，才知道它有多可靠。

## 5. 把经验整理成样板、标准与反馈，供以后复用

复盘做了，记录也写了，常见的结局是躺在文档里，再也没有人打开。想让这些记录被再次使用，整理的时候可以归成三类。

第一类是样板，也就是可以直接参照的成品，比如一份最后被证明有效的方案，一次完整的排查记录。那次站内信的排查，我事后整理成了一份排查清单，列出六个环节和每个环节怎么验证。下次谁遇到类似的问题，照着清单一步一步排查就可以，不必从头摸索。

第二类是标准，也就是结果背后的判断依据：为什么认定这个方案可行，取舍的时候看什么。“跨系统名单中的 ID，要符合目标系统的格式要求，并能识别到预期用户”是一条标准，判断一份方案能不能上线要看哪几项，也是标准。标准比样板更有价值，照着样板只能做出形似的东西，理解了标准，换一个场合也知道该怎么判断。

第三类是反馈，也就是被修正过的地方：方案从第一版改到第五版，哪些内容删掉了、又是为什么删掉的；排查时先走错的方向，后来怎么纠正回来。这类材料最容易被丢弃，恰恰最有价值。成品里只有最后的答案；怎么从不够好改到足够好，那些判断全在修改的过程里。

这三类材料要保存在一个固定的地方，同类的事再出现，先到材料库里找：有样板，照着做；有标准，知道该怎么判断；有修正记录，就不会再走一遍同样的弯路。团队里来了新人，这些材料也可以直接交给他用。经验整理到这个程度，才算真正留了下来。

---

回到“三年工作经验”这件事。同样是三年，有人每件事做完就放下，再也不去想它；有人做完还会回头看一遍：还原过程，追问原因，把经验连同适用条件写下来，验证之后，再存进自己的材料库。这样积累下来，第三年才不会是第一年的重复。
