# 第4章　接到任务，先把“做成什么样”说清楚

“参考以前的做一下”，“把这个流程优化一下”，“这周把报告交了”，工作中的交代常常只有这么几句话。说的人觉得事情很清楚，听的人也觉得不难，直到结果交上来，才发现双方想的根本不是一回事。

没有问清需求就开始做，忙了几天，结果还得重来，换谁都不好受。接到任务时先把要求、时间和需要的支持谈清楚，能省掉不少这样的麻烦。

## 1. 任务听懂了，为什么还要复述一遍？

有一次，我们负责的 APP 要改国内版，我把消息红点的功能交给了临时借调来支援的小 Q。这个功能就是有未读消息时，在消息入口亮起一个小圆点。因为之前海外版已经做过，所以我给他简单介绍了海外版的代码，让他参考着做，其中提到了两个版本的差异，但没有特别强调。他也没再向我确认，便开始了开发。

交上来后，我发现他把海外版这部分代码整个照搬了过来，连红点消失的逻辑也没改：要等所有未读消息都看完，红点才消失；而国内版需要的是打开消息列表就清掉红点。功能能运行，逻辑却不对，只能返工。小 Q 一边听我解释，一边埋怨：你让我参考海外版，又没把差异讲清楚，怎么做完了又说不行？

交代任务的人有责任把要求讲清楚，接任务的人也可以把自己的理解复述一遍，看看跟对方想的是不是一回事。一句“明白了”，并不能说明双方理解一致。漏听一个要求、对同一个词理解不同，或者凭经验补上了对方没说过的条件，都可能让人觉得自己听懂了，却做出了另一个结果。

刚工作的人常担心问得多会显得能力不足，明明有疑问也不敢说。其实，把自己的理解讲出来，请对方确认一下，总比没弄明白就答应下来更让人放心。

复述时，用自己的话讲清要完成什么、关键要求是什么，再请对方核对就行。不必原样重复，更不要求当场给出完整方案。哪里没听懂、哪里拿不准，就接着问清楚。

小 Q 听完任务后，可以先向我复述：“这次要给国内版的消息入口加红点，有未读消息就显示，全部读完后消失。我理解的这两条规则对吗？还有没有漏掉的要求？”

他把“全部读完后消失”说出口时，我就有机会纠正：“国内版打开消息列表就要清掉红点，不用等全部读完。”小 Q 再确认一句“也就是打开列表就清除”，双方才算对上了这条要求。这时纠正一句就够了，不用等代码写完再返工。

## 2. 上级只说了一句话，接下来怎么干？

有时对方只交代了一句话，连具体要做什么都没说清楚。这种情况下，就得继续跟分配任务的人问清楚。

我初中班主任的女儿学金融，实习时遇到过这样一件事。导师只简单交代了用 Python 自动生成 Word 文档的要求，还提到了一个插件。她没问清要生成什么文档、插件用来做什么，就答应下来，随后来问我有没有现成的代码。

我听得一头雾水，便问她：“导师具体是怎么说的？把完整的任务描述发我看看。”她这才把两人的聊天记录发来。我读完发现，导师的要求确实很含糊，连我都没弄明白到底要做什么。她却已经把这件事当成了找一段代码的问题。

单单一句“用 Python 生成 Word”，怎么知道该找什么代码呢？应该先跟导师把任务问清楚，再考虑怎么实现。

**先看清已经知道什么**

可以先把对方的交代和相关材料过一遍，看看哪些要求已经说清，哪些还缺信息。对方提到了工具名字，不代表已经交代清楚要用它干什么。

班主任女儿知道导师想自动生成文档，却不知道文档里应该有什么内容。光听到 Python 和插件的名字，还是不知道要做什么。这时可以先请导师提供一份现有文档，或者说明现在是怎样手工完成这项工作的。先了解正在处理什么事情，才容易发现还缺哪些信息。

**把自己的理解拿给对方确认**

如果根据现有信息有了一个理解，可以把它说出来，直接问对方是不是这个意思。比如“自动生成文档”，究竟是把已有数据填进模板，还是连分析内容也要自动生成？这两种要求对应的工作差别很大，得请导师说清楚。

班主任女儿可以这样问：“我理解是把已有的数据自动填进文档，这样能省掉手工复制、排版的工作，对吗？还是文档里的分析内容也需要自动生成？”如果理解不对，导师就可以直接指出来。完全没思路也不用硬猜，请对方拿一个具体例子讲讲就行。

**先问决定下一步的问题**

疑问可能有很多，不必一次问完。先挑出那些不弄清就没法决定往哪做的问题：这件事想解决什么麻烦，目前最需要处理哪一部分。工具怎么用、某个细节怎么实现，可以在方向明确后继续讨论。有些答案在已有材料里就能找到，可以先查。至于为什么要做这件事、哪些要求更重要，材料里没有说清楚的，就直接问上级。

如果导师仍只是说“就是想自动化一下”，班主任女儿还可以请他具体指出：“现在做这份文档，哪一步最费时间？能不能拿一份文件给我讲一下？”有了具体的文件，双方才知道说的是哪一步操作。等这些讲清楚，再确认插件是否必须使用，才知道接下来该学什么、做什么。

问清任务往往需要几次来回，一开始很难把所有问题都想周全。上级暂时没空，可以先把自己的理解和几个关键问题发给他，等他方便时确认。等待回复时，可以先阅读已有资料。但像“只需要填入数据，还是要生成分析”这样会影响做法的问题，最好先问清楚，再开始写代码。

如果对方回一句“你看着办”，可以把暂定做法写下来发给对方，先在职责范围内做一个小尝试。例如：“我先试着把已有数据填进模板，分析文字暂不自动生成，试好一份再一起看。”涉及扩大任务范围或额外占用资源的事，仍要明确确认，不能因为发过消息就当作已经获准。

遇到“这么简单还要问”，可以缩短问题，说明正在确认哪一处区别、它会影响什么结果。

## 3. 完成线：做到什么程度才算完成？

方向问清楚了，双方对“做完”的定义却未必达成了一致。“这份报告周五交”，可能是周五拿初稿来讨论，也可能是周五就要带着它去见客户。初稿里可以留待讨论的问题，见客户的材料却需要事先核对内容、修改措辞。如果没提前说清楚，就可能一边觉得“我按时交了”，另一边却觉得“这怎么拿得出手”。

所以接任务时，还要说清楚什么时候提交什么、达到哪些要求才算完成。这就是这项任务的“完成线”。

**说清成果的用途和这次的范围**

同样是整理客户反馈，如果只是让同事方便查找原始意见，按类别汇总可能就够了。要是团队拿它决定先改什么，就得归纳出主要问题，还得有依据和建议。问清“给谁用、用来做什么”，才能判断交一张表是否足够，还是需要进一步分析。

接着要划定本次的范围。整理本月反馈，是否还要拿上月作比较；现有记录不完整，是否需要重新联系客户。这些事做不做，会直接影响工作量，不能等做了一半才发现还有这么多要补。先确认这次必须处理哪些，哪些可以留到以后，工作才有明确的边界。

**期限和质量，要说到能检查的程度**

如果周五需要的是可以直接使用的报告，就要把看初稿、提意见和修改的时间留出来。例如约定周三下午先看初稿，周四给出修改意见，周五提交核对后的版本。什么时候需要谁来看、什么时候修改，都提前安排好。

除了交付时间，还要对齐质量要求。我带团队时，会把开发需求的质量要求分成界面、功能和埋点三个部分：界面是否一比一还原了设计稿；测试同事提供的测试用例是否都已自测通过；用户操作是否正确上报了事件和字段。这里说的埋点，就是把用户做了什么操作，以及操作时的相关信息上报给系统。这些都检查过，才能判断质量是否达标。

换成客户反馈报告，检查的内容就不同了。例如，是否覆盖约定时间内的反馈，归纳出的问题能否找到相应原始记录，建议是否回应了这些问题。标准可以来自团队规范或已有的合格样例，再由安排任务的人、实际使用的人共同确认，不需要新人凭空猜一套。

有些工作本身是探索，也可以约定完成线。研究一种自动化方式是否可行，未必能保证交出可用工具，却可以约定先交尝试过的方案、遇到的限制和是否值得继续的判断。把这次要交的是探索结论还是可用成果说清楚，才不会在结尾为“一定得做出来吗”争论。

## 4. 没把握的任务，怎样争取支持？

任务要求都问清楚了，也不代表马上就能动手。有些事没做过，有些业务不了解，自己想了一圈，还是不知道该怎么处理。这时就需要把困难说出来，找有经验的人帮忙。

我入职不久，就接手了一个重点业务模块的维护工作。这个模块对业务很重要，产品经理几乎每个版本都会提新的需求。代码在一次次改动中越堆越多，同一项业务的处理逻辑又散落在不同文件里，每次改需求，都要先花不少时间弄清楚原来是怎么做的。

这样维护下去太费劲，我决定重构，也就是重新整理代码的结构，方便后面继续开发。但重构又有个麻烦：得把原有的业务逻辑梳理清楚，不能漏掉以前为了某些特殊情况加上的处理。与此同时，业务还在不断迭代，能抽出来做重构的只有两个人、三周时间。说实话，我心里一点底都没有。

所以项目刚启动，我就一边梳理方案，一边找团队里的资深同事一起讨论，请他们帮忙看看有没有遗漏、哪些地方需要特别注意。这些同事对业务更熟，能帮助我发现自己没考虑到的问题。

新人刚接手不熟悉的工作，心里没底很正常。求助时，最好把具体卡住的地方讲清楚。是工作量太大，还是没用过某个工具，或者不了解以前为什么这样做？几种情况需要的帮助完全不同，光说“这事有点难”，别人也不知道从哪里帮起。

比如面对旧模块，可以这样问：“我已经看过这部分代码，也有个初步方案，但有几处特殊处理不知道是为什么加的，担心重构时漏掉。能不能请以前做过这部分的同事，帮我讲一下，再看看方案有没有问题？”自己看过什么、哪里还不清楚、希望对方帮什么，都说得具体些，沟通就容易多了。

有时也不需要别人专门指导，只是缺一份旧文档，或者没有查看数据的权限。这些都可以在接任务时一起问清楚。不知道该找谁，可以请上级帮忙找人。找到后，再确认资料什么时候能拿到、权限什么时候能开通。

如果确实缺人、缺时间，或者还需要先研究一下才知道能不能做，就把情况摆出来，跟上级重新讨论范围和排期。先把困难说出来，大家还有办法一起想；一直憋着，等到快交付时才说做不了，就很难安排了。

## 5. 还没做完，要不要先给对方看？

几次讨论之后，目标、范围和时间可能都对齐了，但这些信息有的在聊天里，有的只是口头说过。时间一长，有人记着最初的要求，有人记着后来的补充，做起来还是会有偏差。所以最好把谈好的内容整理一下，发给相关的人确认，后面都按这份记录来做。

简单任务发一条消息就够了。比如整理客户反馈，沟通后可以这样记：

> 这次整理本月的客户反馈，供团队决定优先改进哪些问题。周五下午交分类汇总和改进建议。
>
> 另有一个待确认的问题：是否需要补充上月数据作比较？如果需要，我再核对一下工作量和时间。

哪些定了、哪些还没定，要分开写。影响后续做法的疑问，仍要请对方明确回复。团队已有任务文档，补充在原处就行；后面约定变了，也在同一处更新，并让受影响的人知道。

不过，有些差异写成文字仍然看不出来。双方都同意“把客户反馈分类汇总”，做的人可能按电话、邮件等来源分类，使用的人却想按产品问题分类，好决定先改什么。两边看着同一句话，都觉得没有问题。

与其等整份报告写完，不如先拿少量反馈整理一页，请对方看。分类方式、保留哪些信息、分析写到什么程度，一看就具体了。先确认这一页是否合适，总比整份报告写完才发现分错了类省事。

先做的这一页要有实际内容。只有几个标题，对方也看不出问题；可以选一类问题，把客户原话、归纳和建议完整地写出来，对照约定的完成线，再具体问：“按这样分类，能不能帮助判断哪些问题优先处理？建议还缺什么依据？”同时说明这里只整理了一小部分材料，整体结论仍要等全部材料整理后再判断。

有了明确反馈，就修改这部分内容，把新确认的要求补进记录，再继续展开。如果对方提出增加一轮客户访谈之类的新工作，就重新商量这次要不要做、时间怎么调整。等到交付那天才发现不对，整份报告已经写完，前面的时间就浪费了。

简单的修改，做完检查一下就行。像报告分类这样，一旦想错了，后面整份都得改，才值得先拿一小部分出来确认。

任务只有几句话，就把没说清楚的地方接着聊。双方对完成线达成一致，再开始做，才能少一些“我以为”的返工。
