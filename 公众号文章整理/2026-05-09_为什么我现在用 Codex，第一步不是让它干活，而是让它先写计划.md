## 正文

> TL;DR
>
> 复杂任务里，我现在不会一上来就让 Codex 动手，而是先让它写计划。先把目标、范围和风险对齐清楚，比后面发现方向错了再回滚、重改、重新解释，成本低太多。

刚开始用 Codex 的时候，我最容易犯的一个错误，就是太着急。

任务一丢过去，就希望它立刻开始改。

毕竟都用 Agent 了，不就是想让它少问、快做、多干活吗？

但后来发现，复杂一点的任务里，最麻烦的往往不是它不会做，而是它太快进入执行状态。

ChatGPT 答错了，最多是一段话不对。

Codex 不一样。

它真的会去读文件、改文件、跑命令、推进任务。

如果一开始理解偏了，它不是停在原地偏，而是会沿着那个错误方向一路往前走。

所以我现在用 Codex，遇到稍微复杂一点的任务，第一步通常不是让它直接干活，而是先让它写计划。

OpenAI 官方 Codex 最佳实践里也提到，复杂、模糊、难描述的任务，应该先让 Codex 在开始执行前做计划。

这个习惯看起来简单，但用久了会发现，它能省掉很多后面的返工。

## 最怕的是一开始理解偏了

Codex 执行力很强。

这当然是优点，但也是风险。

如果你给它的任务很模糊，比如：

“帮我优化一下这个功能。”

“帮我重构一下这里。”

“帮我把这篇文章改好。”

它通常不会停下来等你把所有细节解释清楚。

它会自己判断哪些文件相关，哪些地方该改，哪些地方可以顺手优化。

有时候这种主动性很好。

但有时候也很危险。

你只是想让它小修一个问题，它可能顺手改了一大片。

你只是想让它调整一段逻辑，它可能把周边结构也动了。

你只是想让它改一下文章节奏，它可能把原来的表达风格也改没了。

这时候最烦的不是它做得慢。

而是它做得很认真，但一开始方向就不对。

等你发现的时候，它可能已经改了很多东西。

你还得回头看它改了什么，哪里该留，哪里要撤，哪里要重新解释。

所以复杂任务里，我现在会先拦一下。

先别改。

先说说你打算怎么改。

## 计划不是形式，是提前对齐

让 Codex 先写计划，不是为了让它写一份漂亮的步骤说明。

我真正想看的，其实就三件事。

第一，它有没有理解我的目标。

第二，它准备动哪些范围。

第三，它有没有意识到风险。

只要这三件事对得上，后面执行通常就稳很多。

如果计划阶段就发现它理解偏了，修正成本很低。

你补一句就行：

不是这个方向。

这个文件先别动。

这一步先不要做。

但如果等它改完一堆东西以后再发现问题，成本就高了。

所以计划最大的价值，不是让 Codex 显得更专业。

而是把误解提前暴露出来。

很多时候，看一眼它的计划，我就能判断这次任务能不能继续交给它。

如果它连任务边界都说不清，我就不会让它马上动手。

## 我现在一般先让它做三件事

现在遇到复杂任务，我一般会先让 Codex 做三件事。

先读上下文。

不要急着改，先看相关文件，说明现在是什么情况，问题可能在哪里。

再拆步骤。

告诉我准备分几步做，每一步大概解决什么问题。

最后列风险。

哪些地方可能有歧义，哪些改动影响比较大，哪些地方需要我确认。

这三件事做完，我基本就知道它有没有进入正确状态。

如果它理解得对，我就让它继续。

如果它理解得不对，就在计划阶段把方向调回来。

这比等它改完再返工舒服太多。

## 先计划，不是让 Codex 变慢

我一开始也觉得，先写计划是不是有点麻烦。

既然用 Agent，不就是想让它赶紧做吗？

但后来发现，复杂任务里真正浪费时间的，往往不是前面多花几分钟规划。

而是后面发现方向错了，又要回滚、重改、重新解释。

计划不是为了把 Codex 管死。

也不是让它每一步都等你批准。

计划只是先把边界说清楚。

哪里可以改。

哪里不要动。

做完以后怎么确认结果。

边界清楚了，Codex 反而可以更放心地干活。

## 越复杂，越不要急着让它动手

简单任务当然不用这么重。

改一个小 bug，补一段文案，调整一个明确函数，直接做就行。

但只要任务涉及多个文件、多轮判断、长期规则，或者真实业务影响，我现在都会先让 Codex 写计划。

先看它怎么理解目标。

再看它准备怎么拆。

最后看它打算怎么验证。

如果计划都说不清，执行大概率也不会稳。

用 Codex 越久，我越觉得：

真正省时间的，不是让 Agent 一上来就跑得飞快。

而是先确认它跑的方向是对的。
