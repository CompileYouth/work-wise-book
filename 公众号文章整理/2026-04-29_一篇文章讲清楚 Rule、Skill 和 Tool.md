## 正文

> TL;DR
>
> Rule、Skill、Tool 不是替代关系，而是调教 Agent 的三个层次。只堆 Prompt 不够，最后还是得把约束、方法和验证能力搭成一套工作系统。

很多人以为调教 Agent，主要就是继续补 Prompt。但真正决定结果能不能稳定下来的，往往不是你又多写了几条要求，而是你有没有把它放进一套能持续运转的工作系统里。

## 第一阶段：用 Rule 约束 Agent

一开始用 Agent 的时候，很容易有一种错觉：只要我把要求说得足够清楚，它就应该能把事情做好。

所以我们会不断给它补充 Rule。

比如，写文章时不要太像 AI，标题要有传播性，开头要有问题感；写代码时不要改无关文件，改完要自检，不确定的地方不要瞎编；做总结时必须基于原文，不允许扩写，不允许自行脑补。

这些 Rule 当然有用。

因为 Agent 不是人，它没有真正意义上的“默契”。很多你以为理所当然的事情，对它来说都需要被明确写下来。你不说“不要编造”，它可能就会为了让答案更完整而自动补齐；你不说“不要改无关文件”，它可能就会顺手重构一大片；你不说“先理解目标再动手”，它可能一上来就开始执行。

所以调教 Agent 的第一阶段，往往就是给它立 Rule。

但很快你会遇到一个新问题：Rule 越来越多，越来越碎。

今天发现它标题写得不好，就补一条标题 Rule；明天发现它开头太空，就补一条开头 Rule；后天发现它总结时有点飘，又补一条事实边界 Rule。最后这份 Prompt 越写越长，像一本“员工手册”，里面密密麻麻写满了各种禁止事项和注意事项。

问题是，Rule 多了以后，并不一定更好用。

一方面，Rule 太多，Agent 的注意力会被稀释。它不是每次都能把所有 Rule 同等权重地执行到位。另一方面，很多 Rule 之间还会产生隐性冲突。比如你既要求它“表达自然”，又要求它“结构严谨”；既要求它“不要啰嗦”，又要求它“完整覆盖”；既要求它“主动推进”，又要求它“不确定时先问”。这些要求单独看都对，但放在一起，执行起来就没那么简单。

这时候你会发现，单纯靠 Rule 是不够的。

Rule 更适合定义边界，告诉 Agent 什么不能做、什么必须遵守。但如果任务本身比较复杂，只靠一堆规矩，很难让它真正稳定地完成任务。

## 第二阶段：把 Rule 沉淀成 Skill

于是就进入第二阶段：把 Rule 提炼成 Skill。

所谓 Skill，不是把更多 Rule 塞进去，而是把一类任务的经验沉淀成一套方法。

比如你想让 Agent 帮你写公众号文章，如果只是给它一堆 Rule，它可能会机械执行：标题要吸引人、开头要有冲突、段落不要太长、语言要口语化、结尾要有金句。

但这还不够。

真正的写作 Skill 应该包含一套完整的方法：先判断这篇文章要解决什么问题，再判断读者为什么会关心，然后确定唯一主线，再围绕主线设计结构，最后检查每一段是否都在服务这个主线。

这就不再是零散的要求，而是一套办事流程。

同样，代码开发也可以沉淀成 Skill。不是简单告诉 Agent “代码要写好”，而是让它遵循一套步骤：先理解现有架构，再定位最小改动点，再设计实现方案，再修改代码，再运行检查，再说明风险。

Skill 的价值在于，它让 Agent 不只是“遵守 Rule”，而是“知道怎么做事”。

这是一个很重要的变化。

Rule 解决的是“不该怎么做”的问题，Skill 解决的是“应该怎么做”的问题。前者更像约束，后者更像方法论。

但 Skill 也不是终点。

因为只要结果是 AI 生成的，就仍然会有概率不符合预期。它可能看起来遵守了流程，但关键判断错了；它可能结构完整，但内容没抓住重点；它可能代码能写出来，但隐藏了边界问题；它可能输出一篇格式正确的文章，但读起来就是没有人味。

这是 Agent 最容易迷惑人的地方：它经常不是明显错，而是“看起来很对”。

尤其是复杂任务，Agent 的输出往往具备一种表面完整性。标题有，结构有，步骤有，结论也有。但你仔细一看，会发现它可能没有真正解决问题，只是把问题包装成了一个好看的答案。

所以只靠 Skill 还不够。

## 第三阶段：用 Tool 提升确定性

于是就到了第三阶段：给 Agent 使用 Tool。

Tool 的作用，不是让 Agent 更会说，而是让它能做一些确定性的事情。

比如，写完代码之后，不是让它说“我已经完成并自检”，而是让它真的跑测试、跑 Lint、跑 Typecheck。

比如，处理数据时，不是让它凭感觉计算，而是让它调用脚本算出结果。

比如，生成文件时，不是让它口头说明已经生成，而是让它真的创建文件，并检查文件是否存在、格式是否正确。

比如，分析网页时，不是让它凭想象描述页面，而是让它截图、读取 DOM、对比结果。

比如，写基于资料的文章时，不是让它凭记忆总结，而是让它检索原文、引用来源、核对事实。

到了这个阶段，Agent 的工作方式会发生一个明显变化：

以前你是在听它“说自己做完了”。 现在你是在要求它“证明自己做完了”。

这是 Agent 和普通聊天框非常关键的区别。

普通聊天框主要负责生成答案，而 Agent 应该能进入任务现场，调用 Tool，读取文件，修改代码，运行命令，检查结果，再基于反馈继续修正。

也就是说，Tool 补上的不是语言能力，而是验证能力和执行能力。

但 Tool 也不能神化。

Tool 擅长处理确定性的事情，比如代码能不能跑、测试有没有过、文件是否生成、数据是否计算正确、格式是否符合规范。但 Tool 不擅长替你判断方向。

一个产品该不该做，一个功能是不是击中了用户痛点，一篇文章有没有打动人，一个方案是不是值得投入，这些仍然需要人的判断。

所以最终来看，Rule、Skill、Tool 并不是三个彼此替代的阶段，而是三种能力逐渐融合。

Rule 管的是边界，Skill 管的是方法，Tool 管的是验证。真正要搭的，不是越来越长的 Prompt，而是一套能持续产出稳定结果的工作系统。
