## 正文

> TL;DR
>
> 真正会用 Codex，靠的不是某个神奇 Prompt，而是一整套工作方式：任务先说清楚，复杂事先规划，长期规则沉淀进 AGENTS.md，做完再验证，重复流程做成 Skill，稳定之后再自动化。

我原来以为，自己已经把 Codex 用得挺深入了。

但看完 OpenAI 官方这份最佳实践文档后，才发现很多地方只是“用了”，还谈不上“会用”。

真正的 Codex 最佳实践，不是某个神奇 Prompt，而是一整套工作方式：怎么给上下文、怎么沉淀规则、怎么验证结果、怎么接外部工具、怎么把重复流程变成 Skill，最后再自动化。

今天就结合官方的最佳实践，讲讲如何正确地会用 Codex。

## 任务别只说一句话

很多人用 Codex，第一步就太随意。

“帮我改一下。” “帮我优化一下。” “帮我看看哪里有问题。”

这种说法不是不能用，但很容易让 Codex 自己猜。

更好的方式，是一开始就把四件事说清楚：

目标是什么。 上下文在哪里。 有哪些限制。 做到什么程度算完成。

比如你让它改一个功能，不只是说“优化一下”，而是告诉它：这次要解决什么问题，应该看哪些文件，哪些地方不能动，最后要通过什么检查。

任务说得越清楚，Codex 越少瞎猜。

## 复杂任务先规划

简单任务可以直接做。

但复杂任务不要一上来就让它动手。

因为复杂任务真正麻烦的地方，往往不是执行，而是边界没想清楚。

改哪里？不改哪里？有没有风险？要不要拆成几步？这些如果一开始没想清楚，Codex 很可能做着做着就跑偏。

所以遇到复杂任务，先让 Codex 出计划。

甚至可以让它先反问你，把模糊的需求问清楚。

这就像你给一个同事安排复杂任务，不会只说一句“你去搞一下”，而是先对齐目标、范围和步骤。

## 长期规则放进 AGENTS.md

很多人会把所有要求都塞进 Prompt。

这一次告诉它：不要乱改结构。 下一次告诉它：改完要跑测试。 再下一次告诉它：输出前先自查。

问题是，这些规则只要每次都要重新说，就很容易丢。

AGENTS.md 就是用来解决这个问题的。

你可以把它理解成“写给 AI 同事看的项目说明书”。

这里面可以写项目结构、运行方式、测试命令、工程规范、禁止事项、验收标准。

这样 Codex 每次进入项目时，就不用重新从零理解规则。

但 AGENTS.md 不是垃圾桶，不是什么都往里塞。

真正应该写进去的，是以后会反复遇到、而且确实会影响结果的长期规则。

**Prompt 负责这一次，AGENTS.md 负责以后每一次。**

## 配置要固定下来

Codex 不只是靠 Prompt 工作，也靠配置工作。

比如用哪个模型、推理强度多高、权限怎么开、能不能访问外部工具、沙箱限制到什么程度，这些都会影响结果。

如果每次都临时调整，很容易混乱。

稳定的东西应该放进配置里。某一次特殊任务，再临时改。

尤其是权限，不要一开始就开太大。

Codex 越能做事，越要控制它能做什么。

先保持沙箱和审批严格一点，等你确认这个项目、这个流程足够可信，再逐步放开。

## 不要只让它生成，也要让它验证

很多人用 AI，最容易停在“生成”这一步。

代码生成了，文章生成了，方案生成了，好像任务就结束了。

但 Codex 真正适合做闭环。

它不仅可以改东西，也可以检查东西。

在代码场景里，它可以写测试、跑测试、看 lint、看类型检查、review diff。

放到其他工作流里，也是一样。

写文章，不只是生成正文，还要检查标题、开头和结构。 写论文，不只是润色一段，还要检查术语、逻辑和章节衔接。 做面试方案，不只是生成问题，还要检查是否匹配岗位、是否能有效区分候选人。

没有验证的 Codex，只是一个更快的生成器。

做完之后再检查一遍，才更接近一个可靠的工作流。

## 外部信息用 MCP 接进来

Codex 能读项目里的文件，但很多真实工作需要的信息并不在项目里。

可能在文档系统里。 可能在 issue 里。 可能在数据库、监控、设计稿、内部工具里。

如果每次都靠手动复制粘贴，不仅麻烦，还容易过期。

MCP 可以理解成让 Codex 连接外部工具的接口。

但不要一上来就把所有工具都接上。

先看一个问题：

哪些信息是你经常要手动搬给 Codex 的？

如果某个外部信息经常用、经常变、经常复制粘贴，那它才值得接进来。

## 重复工作变成 Skill

如果你发现自己总是在给 Codex 说同一套话，就要警惕了。

每次都按同样方式审稿。 每次都按同样流程分析简历。 每次都按同样标准检查项目。

这时候就不要继续靠长 Prompt 硬撑了。

这种可重复流程，应该变成 Skill。

Skill 可以理解成一套可复用的方法说明。

它告诉 Codex：这个任务什么时候用，输入是什么，输出应该是什么，中间要遵守哪些步骤。

这样下次遇到同类任务，就不用再从头解释一遍。

**如果一个 Prompt 被你反复复制，它就可能应该变成 Skill。**

## 稳定流程再自动化

Skill 解决的是“怎么做”。

Automation 解决的是“什么时候自动做”。

比如每天检查一次某类问题，每周总结一次提交记录，定期生成一次复盘，定时扫描某些异常。

但自动化有一个前提：

这个流程已经足够稳定。

如果一个任务现在还需要你反复纠正、反复补充、反复判断，就不要急着自动化。

先把它变成 Skill。 等流程稳定了，再让它按时间自动跑。

否则自动化只会把不稳定的流程放大。

## 长任务要管好 Session

Codex 的 Session 不只是聊天记录。

它更像一个工作线程，里面积累了上下文、判断、修改和过程。

所以长任务不能乱开。

同一个任务，最好留在同一个 Session 里，因为它能保留前面的上下文。

如果任务真的分叉了，再 Fork 出新的线程。

如果上下文太长，可以压缩。 如果需要让另一个 Agent 做边界清楚的小任务，可以交给 Subagent。

总之，不要把所有事情都塞进一个巨大的对话里。

一个任务一个线程，通常更清楚。

## 最后，避开几个常见坑

很多人用 Codex 出问题，不是模型不够强，而是用法太粗糙。

长期规则一直塞在 Prompt 里。 不给 Codex 运行和验证的方法。 复杂任务跳过规划。 一开始就给它过大的权限。 多个线程同时改同一批文件。 流程还不稳定就急着自动化。 所有任务都堆进一个 Session。

这些错误背后，其实都是同一个问题：

你还是把 Codex 当成一个临时回答问题的 AI，而不是一个需要被配置、被约束、被复盘的工作伙伴。

## Codex 的最佳实践，本质是工作方式升级

这份官方最佳实践看起来讲了很多东西。

Prompt、Plan、AGENTS.md、配置、测试、MCP、Skill、Automation、Session。

但合在一起看，本质上只有一条：

**不要只让 Codex 帮你做一次，而要让它越来越懂你的工作。**

任务说清楚。 复杂事先规划。 长期规则沉淀下来。 做完之后要验证。 重复流程变成 Skill。 稳定流程再自动化。

这样用 Codex，它就不是一个更会写代码的 ChatGPT。

它会慢慢变成一个能理解规则、执行流程、吸收反馈、持续改进的 AI 同事。
