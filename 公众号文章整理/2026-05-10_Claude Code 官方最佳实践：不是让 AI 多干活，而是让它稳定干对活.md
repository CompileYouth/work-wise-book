## 正文

> TL;DR
>
> Claude Code 的最佳实践，本质上不是教你怎么让 AI 多干活，而是教你怎么让它稳定干对活。验证方式、上下文、权限、规则、session 和自动化，这些都不是配角，而是让它长期可用的基础设施。

如果你只是把 Claude Code 当成一个更会写代码的聊天框，那基本还停留在入门阶段。

官方这份最佳实践真正想告诉我们的，不是“怎么写一个更好的 prompt”，而是：**怎么把 Claude Code 当成一个能读代码、改代码、跑命令、验证结果、长期协作的工程伙伴。**

它越能干，越需要你会安排任务、管理上下文、提供验证方式、控制权限和拆分流程。

## 先给 Claude 一个验证结果的方法

这是官方放在最前面的建议，也确实是最重要的一条。

很多人用 Claude Code，只关心它能不能把代码写出来。但真正关键的是：它写完以后，怎么知道自己写对了？

如果你不给它测试、命令、截图、预期输出，它就只能靠语言判断自己有没有完成。这样很容易出现一种情况：它觉得自己做完了，但实际上功能没跑通。

所以你要给它一个可以自查的方式。

比如代码改完后要跑哪个测试，UI 改完后要截图对比，构建错误修完后要重新 build。验证方式越清楚，Claude 越不容易停在“看起来完成”。

**没有验证方式的 Claude Code，只是一个生成器；有验证方式的 Claude Code，才更像一个能闭环的工程助手。**

## 先探索，再计划，最后再写代码

复杂任务不要一上来就让 Claude Code 动手。

这点很重要。

很多时候，任务失败不是因为 Claude 不会写代码，而是它一开始理解错了问题。它可能改错文件，走错方向，或者把本来很小的改动扩大成一场重构。

所以官方建议：复杂任务要先探索，再计划，再实现。

先让 Claude 读相关代码，理解现状。 再让它说明准备怎么改。 最后你确认方向没问题，再让它动手。

这不是为了拖慢速度，而是为了避免它很快地做错一件事。

小任务当然不用这么重。比如改 typo、加日志、改变量名，可以直接做。但只要任务涉及多个文件、业务逻辑或者你自己也不确定方案，就值得先让它 plan 一下。

## Prompt 里要给具体上下文

Claude 很强，但它不会读心。

你只说“帮我修一下这个问题”，它当然也能试，但它需要猜很多东西。

更好的方式是告诉它：问题发生在哪里，相关文件是什么，现有代码有什么模式，修好以后应该是什么状态。

比如你可以说：

“这个 bug 出现在登录后跳转逻辑里，重点看 auth 和 router 相关文件。不要改登录态存储方式。修完后要通过现有登录测试。”

这种 prompt 不一定很长，但信息密度很高。

核心不是写得花，而是减少 Claude 需要猜的空间。

## 给它更丰富的材料

不要只靠文字描述问题。

Claude Code 可以读文件，可以看图片，可以接收 URL，可以通过命令读取日志，也可以用工具获取上下文。

如果你有错误日志，就不要只说“报错了”，直接把日志给它。 如果是 UI 问题，就给截图。 如果有相关文档，就把链接或文件指给它。 如果某个文件很关键，就用 @ 引用它。

这背后的原则很简单：

**你给 Claude 的上下文越接近真实现场，它越容易做对。**

很多失败不是模型能力不够，而是你给它的信息太薄。

## 配好环境，别每次临时凑

Claude Code 不是只靠一句 prompt 工作，它还依赖环境。

比如它能不能跑测试，能不能访问需要的工具，权限怎么控制，项目规则在哪里，常用命令是什么。

这些如果每次都临时告诉它，会很乱。

所以最好把稳定的东西配置好：项目说明、常用命令、权限规则、外部工具、MCP、hooks、skills 等。

这就像你带一个新同事，不会每次都从头讲公司怎么跑项目，而是给他一份清楚的项目说明和可执行环境。

Claude Code 也是一样。

## 写好 CLAUDE.md

CLAUDE.md 可以理解成写给 Claude 的项目说明书。

它不是给人看的 README，而是给 Claude 每次进入项目时看的长期上下文。

里面应该放什么？

放 Claude 靠读代码不容易知道、但又经常影响结果的东西。

比如项目怎么启动，测试怎么跑，代码风格有什么特殊要求，哪些目录不能随便动，PR 有什么约定，项目里有哪些容易踩的坑。

但注意，CLAUDE.md 不是垃圾桶。

不要把所有想法都塞进去。文件越长，Claude 越容易忽略真正重要的东西。

判断一条规则该不该放进去，可以问自己一句：

**如果删掉这句话，Claude 会不会更容易犯错？**

如果答案是否定的，就别放。

## 权限要减少打断，但不能完全失控

Claude Code 会做很多真实操作，比如写文件、跑命令、调用工具。

默认情况下，它会在一些操作前请求你的确认。这很安全，但如果每一步都确认，也会很烦。

官方的思路不是让你完全放开权限，而是让你合理配置权限。

安全、确定、经常要跑的命令，可以放进 allowlist。 风险大的操作，继续保留审批。 更复杂的场景，可以用 sandbox 限制它能访问什么。

这里要把握一个原则：

**Claude 越能做事，越要明确它能做什么、不能做什么。**

不要一上来就给它全权限，也不要每一步都卡死。真正好用的是“有边界的自由”。

## 用好 CLI 工具

Claude Code 很适合和命令行工具配合。

比如 GitHub 的 gh，云服务的 aws、gcloud，监控工具的 CLI，错误追踪工具的 CLI。

为什么 CLI 很重要？

因为它比你复制粘贴信息更高效，也更节省上下文。

你不用把一堆 issue、PR、日志手动复制给 Claude，而是让它通过工具自己查。

更有意思的是，即使 Claude 不熟悉某个 CLI，你也可以让它先看 --help，再尝试使用。

这很像一个工程师接手新工具：先看帮助文档，再解决问题。

## 需要外部系统，就接 MCP

有些上下文不在代码库里。

可能在 Notion。 可能在 Figma。 可能在数据库。 可能在 issue tracker。 也可能在内部系统。

如果这些信息经常要用，每次手动复制就很痛苦。

MCP 就是用来解决这类问题的。

你可以把 MCP 理解成 Claude Code 连接外部工具的一种方式。

但不要一开始就把所有东西都接上。真正应该接的，是那些你反复手动搬运、而且经常变化的信息。

**MCP 不是为了显得高级，而是为了减少高频上下文搬运。**

## 必须每次执行的动作，用 Hooks

有些事不能靠 Claude 自觉。

比如每次改完文件都要跑 eslint。 比如不允许写入某个目录。 比如某类文件一旦修改就必须触发检查。

这种事情不要写在 CLAUDE.md 里祈祷它记得。

应该用 hooks。

CLAUDE.md 更像建议，hooks 更像强制机制。

如果一件事必须发生，而且不能例外，就不要只靠 prompt 或规则文件。直接用 hook 把它固定下来。

这其实是一个很重要的思路：

**能用确定性机制解决的事，不要只靠 AI 记忆。**

## 重复流程做成 Skills

如果你发现自己经常给 Claude 说同一套话，就该考虑 Skill。

比如每次都让它按某种方式修 issue。 每次都让它按某种方式检查代码。 每次都让它按团队特定约定处理 API。

这些不应该每次重新写 prompt。

Skill 的价值，就是把一套可复用的工作方法沉淀下来。

它告诉 Claude：什么时候用，怎么做，输入是什么，输出是什么。

这和 prompt 不一样。

Prompt 更像这一次的任务说明。 Skill 更像一套可以反复调用的方法。

## 用 Subagents 处理隔离任务

有些任务会消耗大量上下文。

比如调查一个复杂 bug，阅读很多文件，检查一类安全问题，或者做一次大范围代码审查。

如果全放在主对话里，主上下文很快会变脏。

这时候可以用 subagent。

你可以把 subagent 理解成一个专门派出去调查或审查的小助手。

它在自己的上下文里工作，最后把结论总结回来。

这样主对话不会被大量中间过程污染。

尤其是做调查类任务时，这个很有用。

## Plugins 是打包好的能力集合

Plugins 可以把 skills、hooks、subagents、MCP servers 等能力打包起来。

也就是说，很多配置不需要你每次自己拼。

如果某个插件已经把一类能力打包好了，安装后就能直接扩展 Claude Code 的能力。

这适合那些比较标准化、可复用的场景。

但使用插件也要有选择，不要一股脑装一堆。工具越多，不代表效果越好，有时候反而会让 Claude 的可用工具变得混乱。

## 像问高级工程师一样问代码库问题

Claude Code 不只是用来改代码的，也很适合帮你理解代码库。

你可以问它：

这个系统的日志是怎么做的？ 新增一个 API endpoint 应该参考哪里？ 这一行为什么这样写？ 这个流程有哪些边界情况？

这类问题非常适合 onboarding。

以前你可能要打扰同事，或者自己翻半天。现在可以先让 Claude 帮你读一遍代码，形成初步理解。

这也是 Claude Code 和普通聊天机器人的区别。

它不是凭空回答，而是基于你的真实代码库回答。

## 大功能先让 Claude 采访你

如果你要做一个比较大的 feature，最糟糕的做法是直接说：

“帮我实现这个功能。”

因为你自己可能都没想清楚细节。

官方推荐一种很好的方式：先让 Claude 采访你。

你给一个粗略目标，让它不断追问你需求、边界、交互、异常情况、技术取舍。

问完以后，让它整理成一份 SPEC.md。

然后再开一个新 session，根据这个 spec 来实现。

这个方法很像正式开发前先写需求文档。

它的好处是：很多模糊点会在开始写代码前暴露出来。

## 及时纠偏，不要看它一路跑偏

Claude 做着做着偏了，不要忍。

越早纠正，成本越低。

如果它刚开始理解错了，你按 Esc 打断，补一句方向，问题就解决了。

如果你等它改完一大堆，再回来纠正，就麻烦了。

官方也提到，如果你在同一个 session 里对同一个问题纠正超过两次，说明上下文可能已经被失败尝试污染了。

这时候不要继续硬拗。

清空上下文，用更清楚的 prompt 重新开始，可能更快。

## 主动管理上下文

上下文是 Claude Code 最关键的资源。

Claude 读过的文件、命令输出、对话历史，都会占上下文。

上下文越乱，表现越容易下降。

所以不要把所有事情都塞进一个 session。

无关任务之间用 /clear。 长任务必要时用 compact。 快速问题可以避免塞进主上下文。 需要分支探索时，用新的 session 或 subagent。

不要觉得“上下文越多越好”。

很多时候，上下文太多，反而会淹没真正重要的信息。

## 用 Rewind 回到正确的位置

Claude Code 有 checkpoints，可以让你回到之前的状态。

这很重要。

因为 Agent 会改文件，改错了就需要回退。

Rewind 可以恢复对话、代码，或者两者都恢复。

但要注意，checkpoints 不能替代 git。

它只跟踪 Claude 做出的修改，不一定覆盖外部进程带来的变化。

所以重要工作还是要配合 git 使用。

可以把 rewind 理解成局部后悔药，把 git 理解成正式版本管理。

## 给 Session 命名，并按工作流保存

Claude Code 的 session 是可以恢复的。

这意味着你不需要每次都重新解释一个长期任务。

如果一个工作会持续几天，或者以后还会回来处理，就给 session 起个清楚的名字。

把 session 当成一个工作分支。

比如一个 session 专门处理登录改造，一个 session 专门处理性能优化，一个 session 专门处理某个迁移任务。

这样下次回来时，Claude 能接上之前的上下文。

## 用 Non-interactive Mode 做自动化

Claude Code 不只能在交互式窗口里用。

它也可以通过 claude -p 这种方式在脚本、CI、pre-commit hooks 里运行。

这适合把某些检查或自动化任务接进工程流程。

比如提交前让 Claude 做一次检查，CI 里让 Claude 总结失败原因，脚本里让 Claude 批量处理某类问题。

但这类自动化要谨慎。

因为没有人在旁边实时接管，所以权限、工具范围和输出格式都要设计好。

## 多开 Session，但要隔离

多个 Claude session 可以并行工作。

但并行不是简单多开窗口。

如果多个 session 同时改同一批文件，很容易冲突。

所以要用 worktree、隔离环境或明确分工。

多 session 最适合两类场景。

一种是并行探索不同方向。 另一种是 Writer / Reviewer 模式：一个 session 实现，另一个 fresh context 的 session 审查。

后者很有价值，因为 Reviewer 没参与实现，反而更容易发现问题。

## 大规模任务可以 Fan out

如果你要做大规模迁移，比如一批文件都要按某种规则修改，可以用 fan-out 模式。

先生成任务列表。 再写脚本遍历每个文件调用 Claude。 先在少量文件上试，调整 prompt，再跑全量。

这里最重要的是控制权限和范围。

大规模自动执行时，不能让 Claude 想干什么就干什么。

要用 --allowedTools 之类的方式限制它能做的事。

## Auto Mode 适合后台执行，但不是无脑放权

Auto mode 可以让 Claude 在安全检查下更连续地执行任务。

它会用 classifier 判断某些命令是否有风险。

这能减少审批中断，让 Claude 更顺畅地推进。

但这不代表可以无脑放权。

Auto mode 适合边界清楚、风险可控的任务。

如果任务本身很模糊，或者可能触碰生产环境、基础设施、敏感数据，就不能随便让它后台乱跑。

## 避免几个常见失败模式

官方最后总结了一些常见坑，其实都很典型。

不要一个 session 里塞所有任务。 不要在同一个失败方向上反复纠正。 不要把 CLAUDE.md 写成巨长说明书。 不要相信看起来合理的输出，必须给验证方式。 不要让 Claude 无范围地无限探索代码库。

这些问题背后是同一个原因：

你没有管理好上下文、边界和反馈。

Claude Code 越强，越不能粗放使用。

## 最后，要培养自己的使用直觉

官方最后一条其实很重要。

这些最佳实践不是死规则。

有时候你需要清空上下文，有时候需要保留上下文。 有时候要先规划，有时候可以直接动手。 有时候 prompt 要很具体，有时候可以故意开放一点，让 Claude 自己探索。

真正会用 Claude Code，不是背一堆规则，而是慢慢形成判断。

你要观察：

什么时候它表现好？ 什么时候它开始跑偏？ 什么时候该清上下文？ 什么时候该让 subagent 去调查？ 什么时候该收紧权限？

这些直觉只能在真实使用里长出来。

## 总结

Claude Code 的最佳实践，看起来讲了很多东西。

验证、规划、上下文、CLAUDE.md、权限、MCP、hooks、skills、subagents、sessions、automation。

但如果压缩成一句话，其实就是：

**不要把 Claude Code 当成一个只会回答问题的 AI，而要把它当成一个需要被带、被约束、被验证、被复盘的工程同事。**

你给它上下文，它才能理解现场。 你给它验证方式，它才能闭环。 你给它规则和工具，它才能稳定工作。 你管理好 session，它才不会被上下文拖垮。

Claude Code 越强，越需要你会带它。 这大概就是这份最佳实践真正想教我们的事。
