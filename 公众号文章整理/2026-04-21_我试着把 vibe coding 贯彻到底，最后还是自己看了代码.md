## 正文

> TL;DR
>
> Vibe Coding 看起来像是把需求讲清楚，剩下就交给 AI 往下做。但真正复杂一点的项目里，决定结果质量的往往不是有没有做，而是具体怎么做。需求能保证方向不偏，关键实现对不对，最后还是得有人判断。

很多人觉得 Vibe Coding 很简单，有嘴就行，但是我觉得事情没那么简单。

前段时间我在用 AI 做一个项目：根据用户上传的素材，再结合背景音乐的节拍，自动生成一段视频。这个需求乍一看特别适合 Vibe Coding。因为它很容易描述：素材、节拍、卡点、转场、时长，感觉只要把需求讲清楚，剩下的就是让 AI 往下做。

所以我一开始真是这么想的。我没有急着自己下场写，而是尽量把 Vibe Coding 发挥到底。先跟 AI 反复沟通需求，再让它出设计文档，我自己逐条确认。那份文档当时看下来其实挺让我放心的，流程、模块、关键逻辑，基本都符合我的预期。我当时甚至觉得，这次应该稳了。

但后面真正生成出来的视频结果，还是不对。

也不是完全错了，不是说做成了另一个东西，而是那种很微妙的落差：你能看出来它在往你想要的方向靠，表面上的东西也都有了，但最终成片就是差点意思。节拍不够准，素材切换不够舒服，有些地方逻辑上说得通，但观感上不行。总之就是，文档看着对，结果却不对。

一开始我还挺相信这套方式的。我想，这不就是 Vibe Coding 最擅长的吗？继续沟通，继续调。于是我一轮轮给反馈：这里不自然，那里节奏不对，这种切法不符合预期。AI 每次也都说理解了，然后开始改。

但改了几轮之后，我慢慢发现一个问题：它确实一直在改，但很多改动更像是在表层打补丁。你说这块不对，它就修这块；你说那里不舒服，它就再调一下参数。可核心问题其实没动到。每一轮看起来都变了一点，但始终没有那种“终于改到点上了”的感觉。

最后没办法，我还是让它把关键实现吐出来给我看。

这一看，很多事情就清楚了。问题不是什么玄学，也不是什么审美差异，而是实现里确实有几处明显的问题。有的地方逻辑看着没毛病，但实现策略本身就不合理；有的地方虽然功能做到了，但方式太粗，天然就会导致结果差；还有些地方，它选了一个很通用的方案，写 demo 可以，放到这个具体场景里就不够对。

看到这里我才真正反应过来：Vibe Coding 最大的误导，可能就在于它很容易让人以为，只要沟通足够充分、设计文档确认过了，后面的实现就只是体力活。可实际上不是。尤其是稍微复杂一点的项目，真正决定结果质量的，往往不是“有没有做”，而是“具体怎么做”。

而“怎么做”这件事，本质上就是技术判断。

所以我现在越来越觉得，Vibe Coding 不是两眼一抹黑地指挥 AI 做个东西出来。简单场景当然没问题，搭个页面、写个小工具、做个 demo，很多时候确实很爽。但只要复杂度一上来，尤其是这种结果质量特别依赖实现细节的项目，你就不能只停留在“我已经把需求讲清楚了”这一步。因为需求清楚，只能保证方向不偏；实现对不对，还是得有人判断。

而且这个判断，很多时候不是判断“它有没有做”，而是判断“它是不是这么做对”。这两件事差别很大。AI 往往不会漏掉特别显眼的功能，但很容易在关键实现上选一个“差不多”的方案。这个方案在文字描述里很顺，在代码里也能自圆其说，甚至跑起来都没报错，可结果就是不够好。

所以我现在对 Vibe Coding 的理解变了。我并不觉得它没用，我还是会继续大量用。它在快速铺方案、快速搭骨架、快速把东西推进到可运行状态这件事上，真的很强。但我不会再把它理解成“我只负责提需求，剩下都交给 AI”。

说到底，Vibe Coding 不是不要技术了，而是更考验你有没有技术判断。你可以不亲手写完所有代码，但你最好知道，什么地方可以继续跟 AI 聊，什么地方必须把关键实现拎出来自己看。

AI 可以替你干活，但替代不了你在关键处做判断。这个可能才是 Vibe Coding 真正难的地方。
